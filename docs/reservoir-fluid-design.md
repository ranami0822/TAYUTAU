## 1. 目的

- 流体の方程式を、リザバー（ESN）で近似し、計算量を減らす。
- 流体だけにこだわったシミュレータを、ゲームとして作る。
  - 水を炙ると沸騰する。
  - 状態方程式を守る。
  - 凍る。フローズンにできる。
- 動作環境はブラウザ（WebGPU）。
- 見た目がそれらしく、破綻しないことを優先する（工学的な精度は目的にしない）。
  精度が目的だと、リザバーが保存則を保証しない点が壁になる。

## 2. 基本アーキテクチャ（ハイブリッド）

物理層とリザバー層に分ける。

### 物理層（明示的に書く）
- 水の状態方程式（Tait型など）。
- エンタルピー法で、温度と潜熱を扱う。
- 凍結は Stefan 問題として、エンタルピー法で解く。
- 凍結率が閾値を超えた領域を固体扱いにする（フローズン化）。
- 質量とエネルギーの保存は、この層が保証する。

### リザバー層（学習させる）
- 対流、乱れ、泡のような、粗い格子では解像できない部分の補正（クロージャ）を担当する。
- 沸騰や相変化そのものをリザバーに学習させない。

### リザバーの使い方
1. 流れ場（渦度など）をPCAかオートエンコーダで低次元に圧縮する。
2. その潜在状態の次ステップをリザバーで予測する。
3. デコードして描画する。
4. 広い領域は、タイルごとに小さなリザバーを置き、隣同士を結合する（Pathak ら 2018 の並列リザバーが起点）。
5. 精度が要る部分は、粗い物理モデルとのハイブリッドにする。

### 利点と難点
- 利点: 1ステップが疎行列×ベクトルで、圧力ポアソン方程式を解く工程がない。学習はリッジ回帰で済む。
- 難点: 非圧縮性や保存則が自動では守られない。長く回すと発散しやすい。学習に本物のソルバーのデータが必要。境界条件や形状が変わると汎化しにくい。格子全体を1つのリザバーで扱うと次元が足りない。

## 3. 発散対策

### 提案された案
リザバーを「別のカオス」で制御し、フィードバックして発散を防ぐ。

### 評価（会話中のClaudeの見立て。実証済みではない）
- カオス制御（OGY法や遅延フィードバック）は、目標となる軌道があって初めて安定化できる。
- リザバーの暴走は、状態が学習した領域から外れることが原因。外から別のカオスを足しても、正しい領域は分からない。安定する保証がない。

### 効きそうな手段
- 毎ステップ、拘束条件へ射影する（発散ゼロ化、質量・エネルギーの補正、値のクランプ）。最も確実。
- 学習時にノイズを入れて、誤差に強い重みにする。
- 粗い物理ソルバーの結果へ軽く引き戻す（ナッジング）。
- 状態が学習領域から外れたかを監視し、外れたら引き戻すか再初期化する。

### 提案案に近い形
第2の小さなリザバーを「補正器」にする。
- 入力: メインの状態。
- 出力: 補正量。
- 学習: 「ずれた状態 → 正しい状態」のペアで学習する。
- これはカオス制御というより学習型フィードバック。試す価値はある。

## 4. 技術スタック

重い計算はWGSLのコンピュートシェーダーで書く。そのため、ホスト側の言語による速度差はほぼない。違いは開発体験と連携のしやすさ。

| 選択肢 | 要点 |
|---|---|
| **Babylon.js + WebGPU（推奨）** | WebGPUEngineの`ComputeShader`と`StorageBuffer`で、シミュと描画を同じGPU上で完結できる。場をCPUに戻さずマテリアルへ渡せる。WebGPUが使えない環境ではコンピュートが動かない（WebGL2へのフォールバックは非現実的）。 |
| 生のWebGPU（TS） | 自由度は最大だが、描画まで自作。Babylonと混ぜるなら同じデバイスを共有する（別デバイスだとバッファ共有ができない）。 |
| Rust（wgpu） | WASMでブラウザのWebGPUに載り、同じコードがネイティブでも動く。WGSLも流用可。Babylonとはデバイスが別になるので、描画まで全部wgpuで書く。ネイティブ版も出したい場合や、CPU側の重い処理を同じ言語にしたい場合向き。 |
| Zig | WebGPU周りのエコシステムがまだ薄く、ブラウザ向けには弱い。Dawnを使ったネイティブ寄りの構成が中心。[未確認: 最新状況] |

### 方針
- まずBabylon.js + WebGPUでブラウザ上で動く検証を作る。
- WGSLカーネルを固めてから、必要ならRust（wgpu）に移植する（WGSLは流用できる）。
- リザバーの学習（リッジ回帰）はPythonでオフラインに行い、重みだけをブラウザへ持ち込む。
- 実行時のリザバー1ステップは、WebGPU上の疎行列×ベクトル。

## 5. AIにリザバーを実装させる手順

- 標準的なESN（リーク付き更新式、リッジ回帰の読み出し）は、AIが知っていて数十行で書ける。論文なしでよい。
- 新しい手法（並列・階層リザバー、ハイブリッド型、NVAR（次世代リザバー）、PDE向けの局所結合）は、論文を読ませる。

手順:
1. 論文のPDFか、arXivのソース（LaTeX）を渡す。数式はLaTeXのほうが読み違いが減る。
2. まず実装させず、「アルゴリズムを、式、変数の形（shape）、擬似コードで書き直して」と頼む。
3. 書き直しを、人間が論文と見比べて確認する。
4. そのあとで実装させる。
5. 検証は論文の再現で行う。最小の検証はLorenz系（論文の図に近づくか。予測できる長さをリアプノフ時間の何倍かで見る）。再現できてから、自分の改造に進む。

注意:
- 論文に書かれていない細かい設定（スペクトル半径、正則化の値など）は、AIに推測で埋めさせず、「論文に書いていない」と明示させる。
- 参考実装: ReservoirPy（Python）、ReservoirComputing.jl（Julia）。Pathakらの研究コードも公開されていたと記憶しているが、現状は未確認。答え合わせの基準にする。

## 6. 調査をAIに任せるとき

専門外のため、AIの出力の正しさを自分で判断しにくい。次のようにする。
- 主張ごとに、論文のタイトル、著者、arXiv IDかURLを付けさせる。実在するかを数件開いて確かめる（存在しない論文を作ることがある）。
- 「確立している話」「1本の論文だけの主張」「AIの推測」を分けて書かせる。
- 方針を決める重要な点は、文章で納得せず、小さな実験で確かめる。

## 7. デプロイ

- 候補: GitHub Pages（公開）、Cloudflare Workers（静的アセット）。独自ドメインがある。
- WebGPUの計算はブラウザ側で動くので、どちらも静的配信で足りる。
- **Workersを選ぶ**。独自ドメインを付けやすい。レスポンスヘッダーを自由に設定できる。あとからAPIや保存機能を足せる。
- GitHub Pagesは、無料プランだとリポジトリが公開になり、ヘッダーの自由度が低い。
- 注意: Workersの静的アセットには、1ファイルあたり約25MiBの上限があったと記憶している。[未確認]
  重みファイルが大きいときは、公式ドキュメントで確認する。重みは小さく保つ（疎な結合、半精度）。

## 8. 最初の実験案

2D水面に熱源を置く。
- 温度が上がると対流する。
- 閾値で、沸騰するか凍結する。

進め方の候補:
1. Pythonで、小さな系（Lorenz系や2D渦）のリザバーを学習し、論文の再現を確認する。
2. 粗い物理ソルバーと組み合わせるハイブリッドにし、射影とナッジングで発散を抑える。
3. WGSLに移して、ブラウザで動かす。
